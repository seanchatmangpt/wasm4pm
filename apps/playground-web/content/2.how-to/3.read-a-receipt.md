# Read a BLAKE3 Receipt

Every algorithm run in the playground produces a **receipt** — a small JSON document that proves the computation happened and records exactly what went in and came out. Receipts use BLAKE3 hashing for speed and collision resistance.

## The Receipt Viewer

The receipt panel appears automatically after each successful run. You can also open it by clicking the **Receipt** tab at the bottom of any algorithm result panel.

::ReceiptViewer{}

Click **Copy JSON** to copy the full receipt to your clipboard. This is useful for filing bug reports (paste the receipt alongside the log preset name) or for archiving computation proof alongside your analysis artefacts.

## Field Reference

A typical receipt looks like this:

```json
{
  "run_id": "01J3KZ9VHXQ7Y2MNPF8RBTD04E",
  "algorithm": "alpha_miner",
  "timestamp": "2026-06-10T09:14:22.418Z",
  "input_hash": "a3f8c2e14d7b9056f1a2c3d4e5f60718293a4b5c6d7e8f901234567890abcdef",
  "output_hash": "7d4e2c9b1a6f830547e29c1d3a58b7f60e94d2c1b3a5f7e9012345678901abcd",
  "input_size": 14832,
  "duration_ms": 12
}
```

### `run_id`

A [ULID](https://github.com/ulid/spec) (Universally Unique Lexicographically Sortable Identifier). ULIDs are 26-character base32 strings that sort chronologically. The first 10 characters encode the millisecond timestamp of the run; the remaining 16 are random. This means a list of receipts sorted lexicographically is also sorted by time.

### `algorithm`

The algorithm identifier as registered in the wasm4pm kernel registry. Matches the `algorithm` field you selected in the UI.

### `timestamp`

ISO 8601 UTC timestamp of when the run completed, to millisecond precision. The timestamp is embedded in the `run_id` as well — they will always agree to within one millisecond.

### `input_hash`

A 64-character (256-bit) BLAKE3 hex digest of the raw input bytes fed to the algorithm. For XES logs this is the UTF-8 bytes of the XML string; for OCEL JSON it is the canonical JSON bytes (keys sorted, no extra whitespace).

The input hash is computed before any parsing. If two runs have the same `input_hash`, they processed byte-identical input.

### `output_hash`

A 64-character BLAKE3 hex digest of the algorithm's serialised output. For Petri net discovery algorithms this covers the full PNML XML string. For DFG algorithms it covers the adjacency JSON.

**Determinism guarantee:** Same `input_hash` + same `algorithm` + same wasm4pm version must always produce the same `output_hash`. If they do not, that is a determinism defect — please report it.

### `input_size`

The byte length of the raw input. Useful for estimating memory usage and for confirming you loaded the log you intended (a 15 KB log versus a 15 MB log will have very different `input_size` values).

### `duration_ms`

Wall-clock milliseconds from algorithm invocation to serialised output, measured inside the WASM module. This excludes browser rendering time.

## How Receipts Chain

Each run's `output_hash` can serve as proof of computation for a downstream run. For example:

```
Run 1: load log          → output_hash = H1
Run 2: alpha_miner(H1)   → input_hash = H1, output_hash = H2
Run 3: conformance(H2)   → input_hash = H2, output_hash = H3
```

This chain is tamper-evident: altering any intermediate output invalidates all subsequent `input_hash` values. The playground does not automatically chain receipts across runs, but you can verify the chain manually by comparing `output_hash` of run N with `input_hash` of run N+1.

## Verifying a Receipt

To confirm a result is reproducible:

1. Note the `input_hash` and `output_hash` from the original receipt.
2. Reload the exact same log (same file bytes — use the same preset or re-drag the same file).
3. Run the same algorithm.
4. Compare the new receipt's `input_hash` and `output_hash` to the originals.

They must be identical. If `input_hash` matches but `output_hash` differs, the algorithm is non-deterministic in your browser environment — this is a defect. If `input_hash` differs, the input was not byte-identical (check encoding, line endings, or preset version).

## Receipts Outside the Playground

When using the `wpm` CLI, receipts are written to `.wasm4pm/receipts/latest.json` after every run. The JSON schema is identical to what the playground displays.

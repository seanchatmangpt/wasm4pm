# Object-Centric Process Mining

Classical process mining assumes every event belongs to exactly one case. Real processes — order fulfilment, supply chain, healthcare pathways — involve events that touch multiple objects simultaneously. Object-Centric Event Logs (OCEL 2.0) capture this many-to-many reality. This guide covers when to use OCEL, how to load it in the playground, and how to read the results.

## OCEL 2.0 vs XES: When to Use Each

| Criterion | Use XES | Use OCEL 2.0 |
|-----------|---------|--------------|
| One case notion dominates (e.g. case ID) | Yes | No |
| Events touch multiple objects simultaneously | No | Yes |
| You need convergence/divergence analysis | No | Yes |
| Your source system is a relational DB or ERP | Sometimes | Preferred |
| You want classical Petri net conformance checking | Yes | Partial |
| Object lifecycles matter (orders, items, routes) | No | Yes |

If you are unsure, start with XES. If your directly-follows graph looks like spaghetti because the same event appears under many case IDs, switch to OCEL — you likely have a many-to-many case-to-event relationship that XES cannot model cleanly.

## OCEL 2.0 JSON Structure

The playground accepts OCEL 2.0 JSON with the following top-level structure:

```json
{
  "ocel:global-log": {
    "ocel:object-types": ["Order", "Item", "Route"]
  },
  "ocel:events": {
    "e1": {
      "ocel:activity": "Place Order",
      "ocel:timestamp": "2026-01-15T08:00:00Z",
      "ocel:omap": ["o1"],
      "ocel:vmap": {}
    }
  },
  "ocel:objects": {
    "o1": { "ocel:type": "Order", "ocel:ovmap": { "value": 420.00 } },
    "i1": { "ocel:type": "Item",  "ocel:ovmap": { "sku": "A-100" } }
  }
}
```

Key points:
- `ocel:omap` links each event to one or more object IDs — this is where the many-to-many relationship lives.
- Object types are declared in `ocel:global-log` and must match the `ocel:type` values in `ocel:objects`.
- Timestamps must be ISO 8601 with timezone.

## Loading OCEL in the Sandbox

1. Open the **Presets** dropdown and select **ocel-example**, or drag-drop your own `.json` file.
2. The log panel shows the **OCEL 2.0** badge and displays object-type counts instead of a single case count.
3. The algorithm selector automatically filters to OCEL-compatible algorithms: `ocel_dfg`, `ocel_inductive_miner`, and `ocel_conformance`.

## Running ocel_dfg

The Object-Centric Directly-Follows Graph (`ocel_dfg`) builds one DFG per object type and overlays them with shared event nodes. This gives you a per-type flow view without flattening the log.

::AlgorithmDemo{algorithm="ocel_dfg" preset="ocel-example"}

The result panel shows:
- A tab for each object type (e.g. **Order**, **Item**, **Route**).
- Arc weights = number of times object of that type moved between two activities.
- Shared events (events in `ocel:omap` for multiple object types) appear with a multi-type border.

## Running ocel_inductive_miner

`ocel_inductive_miner` applies the Inductive Miner recursion per object type and produces a per-type process tree. It then computes **inter-type synchronisation edges** where events are shared.

Select `ocel_inductive_miner` from the algorithm panel dropdown and click **Run**. The result is a set of process trees — one per object type — with synchronisation arcs shown as dashed edges between trees.

## Interpreting Object-Centric Results

### Multiple Object Types

Each object type has its own process model. An "Order" type might have a simple linear flow (Place → Confirm → Ship → Deliver) while the "Item" type shows a loop (Pick → Re-pick → Pack). These are correct simultaneous truths about the same process.

### Convergence

**Convergence** happens when multiple objects of different types synchronise at a single event. Example: a `Pack Items` event that touches both an `Order` object and several `Item` objects. In the DFG view, converging events appear with inbound arcs from multiple object type swimlanes.

High convergence at a single activity is often a bottleneck signal — that activity must wait for all converging objects to be ready.

### Divergence

**Divergence** happens when one event fans out to multiple objects. Example: a `Split Shipment` event that creates multiple `Route` objects from a single `Order`. In the result panel, diverging events show multiple outbound arcs to different object type swimlanes.

Unexpected divergence (divergence not in the declared process model) is a conformance signal — investigate whether the split is intentional or a data-quality issue.

### Object Lifecycle Soundness

The quality panel for OCEL algorithms includes an **Object Lifecycle** score. A score of 1.0 means every object of each type has a lawful start and end activity with no unresolved open cases. A score below 1.0 means some objects have incomplete lifecycles in the log — either the log is truncated, or objects are created/consumed outside the logged window.

## Exporting OCEL Results

Use **Export OC-PNML** to download the object-centric Petri net in the OCEL Petri net format supported by pm4py. You can then run `pm4py.conformance_diagnostics_alignments_ocel()` on your full dataset using the discovered model.

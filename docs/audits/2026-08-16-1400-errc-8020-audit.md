## 3. What NOT to Do (traps)

- **Splitting `reinforcement.rs` + `rl_orchestrator.rs` by concern** (L/L, score 1.0) — the two largest RL files in the repo look like an obvious target because of sheer size, but the raw finding itself rates impact as only L, not the payoff the effort suggests. Wait until something more concrete (a bug, a duplicated bandit implementation) forces the split.
- **Reducing the nine `apps/wasm4pm/src/commands/*.ts` files** (55K lines, L/L, score 1.0) — the "one shared extraction fixes nine files" framing makes this sound efficient, but it's still a large, cross-cutting refactor of actively-used CLI surfaces. Don't let the line-count size trigger urgency disproportionate to its score.
- **Consolidating the five `oracle_impls/*.rs` breed files** (score 0.67) — "near-identical block counts" reads like an obvious macro/trait-default opportunity, but touching five ~1000-line files simultaneously is real regression risk for a score below several smaller, cleaner wins.
- **Standing automation for `integration/finish-wip-*` triage** (score 0.67) — solving the recurring-incomplete-work pattern with a new automated system is tempting as a "fix the root cause" move, but it requires real build investment. Do the cheap branch cleanup (top-5 move #2) first; only build automation if the pattern recurs after that.

## 4. Recommendation for This Audit's Own Scope

This audit currently re-scans the entire repository from scratch every hour across five independent dimensions, which means most of each run's cost is spent re-deriving findings that haven't changed since the last run — CI workflow topology, branch staleness, and doc cross-reference gaps move on the order of days, not hours. Next iteration should (1) diff against the prior run's finding set and report only new/resolved/changed findings by default, with the full grid available on demand, so an hourly cadence actually tracks drift instead of restating a static snapshot; (2) scope the code-complexity and dead-code scanners to files touched since the last run (`git diff --stat` against the last audit's commit SHA) rather than a full-repo sweep, since those are the two categories most likely to shift hour-to-hour as active work lands; (3) leave the CI-friction, branch-hygiene, and docs-onboarding scanners on a slower cadence (daily, not hourly) since their underlying signals — workflow file count, branch staleness, doc consistency — genuinely don't change on an hourly clock, and running them hourly is pure waste; and (4) persist a small findings ledger (location + category + first-seen + last-seen timestamps) so a finding that's been sitting at the same leverage_score for a week gets flagged as "stale/ignored" rather than re-reported identically forever, which is the actual signal an hourly recurring audit should be optimized to surface.

## 6. Is "Always Full Sweep" Still Earning Its Cost at Run 4?

Worse, not better. Run 3 already measured ~90% restatement; this run's actual net-new information reduces to a single settled fact (no `.mcp.json` exists anywhere in the repo — a one-command check, not a sweep). Every other line in this run's 53-finding, 5-category JSON payload is a re-derivation of state that was already known and already scored in run 3, at matching or near-matching leverage scores, on files that have not changed (ci.yml:46 is byte-identical to its run-3 form; branch count moved by natural accretion, not by anything the audit caused; ADR-002 is intentionally frozen pending a human decision that no audit run can substitute for). The marginal value of this specific run is real but narrow: it converts one ambiguous prior claim into a verified one. That is a legitimate contribution, but it is disproportionate to the cost of re-scanning ~50 findings across 5 categories to produce it. Diminishing returns compound with each unresolved run, because none of the top-leverage items (ci.yml fix, MCP registration, ADR-002) require rediscovery — they require someone to spend the 10 minutes actually applying the one-line/one-config fixes already identified twice. A tighter policy — diff-scoped sweep unless the user names a category, plus a standing "verify top-5-from-last-run" step in place of full re-derivation — would likely preserve this run's one useful output (the MCP-registration confirmation) at a fraction of the token cost, while an unconditional full sweep at hourly cadence is now producing mostly restatement with a shrinking confirmation payoff each cycle.

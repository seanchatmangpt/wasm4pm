# workspace-pack

Cross-product pack: every wasm4pm Cargo-workspace crate x {README header
stub, CI check-matrix job fragment, registry doc}.

## What it generates

`packs/workspace-pack/ontology.ttl` declares `compat:WorkspaceCrate` and
carries one individual per real crate in this workspace (9 as of the
2026-08-13 survey: the root `wasm4pm` crate plus 8 `crates/*` members).
Three `[[generation.rules]]` entries in the root `ggen.toml` drive three
templates off that same query result set:

| Rule | Template | Output |
|---|---|---|
| `workspace-crate-readme-headers` | `crate-readme-header.md.tera` | `docs/crates/{{ crateDir }}/README-header.md` (one per crate) |
| `workspace-crate-ci-jobs` | `crate-ci-job.yml.tera` | `.specify/generated/ci-jobs/{{ crateDir\|replace }}.yml` (one per crate) |
| `workspace-crate-registry` | `workspace-crate-registry.md.tera` | `docs/workspace-crate-registry.md` (single doc, all crates) |

## Safety properties

- All three output paths are new/additive, entirely outside
  `crates/*/src/`, `wasm4pm/src/`, and any `Cargo.toml` — nothing
  hand-written is at risk from a re-run.
- `crate-readme-header.md.tera` explicitly renders to
  `docs/crates/<dir>/README-header.md`, never `<dir>/README.md` — a crate's
  real, hand-written README is never touched.
- `crate-ci-job.yml.tera` renders a `jobs:`-body fragment only (no
  `on:`/top-level `name:`), matching `github-actions-pack`'s `gha:Job`
  layer so it composes with, rather than conflicts with, the existing
  `ci-workflows-render` rule and `.specify/ci-workflows.ttl`. It is not a
  standalone runnable workflow; splice it under a real `jobs:` key by hand
  or via that pack's own conventions.
- `mode = "Overwrite"` on all three rules is correct specifically because
  every output is a pure derivation of `ontology.ttl` — re-running is
  idempotent and never clobbers anything not itself generated by this
  pack.

## Re-surveying the workspace

There is no live `cargo metadata` query wired into `ggen sync` yet.
`ontology.ttl` is a checked-in survey snapshot: when a crate is added,
removed, or its `Cargo.toml` `package.description`/`package.name` changes,
edit the corresponding `compat:WorkspaceCrate` individual (or add/remove
one) by hand, then re-run `ggen sync run`.

## Query and template sourcing

Both `query` and `template` in this pack's `[[generation.rules]]` entries
use `{ file = ... }` sourcing (`QuerySource::File` / `TemplateSource::File`),
never `{ pack = ... }` — the same convention already used by this repo's
`paper-fidelity-docs` and `ci-workflows-render` rules, whose comments
record that `QuerySource::Pack` hits FM-GEN-006 and `TemplateSource::Pack`
hits FM-GEN-007 on ggen 26.8.8. `file =` is the only combination confirmed
to actually render.

## Files

- `pack.toml` — pack metadata.
- `qualification.toml` — consumer-union contract (nothing to union; this
  pack ships its own individuals).
- `ontology.ttl` — `compat:WorkspaceCrate` class, properties, and the 9
  real workspace-crate individuals.
- `queries/extract-workspace-crates.rq` — one row per crate, ordered by
  `crateDir` for deterministic, byte-for-byte-repeatable output.
- `templates/crate-readme-header.md.tera` — per-crate README stub.
- `templates/crate-ci-job.yml.tera` — per-crate CI job fragment.
- `templates/workspace-crate-registry.md.tera` — whole-result-set registry
  doc, looping the `sparql_results` binding (confirmed against
  `wasm4pm-compat/ggen/templates-breeds/registry.json.tera` and
  `breed-registration.rs.tera`, both real single-file, multi-row renders
  in this ecosystem).

# Compare Discovery Algorithms

The playground lets you run several discovery algorithms against the same loaded log and compare their output models. This guide explains how to do that and what the quality dimensions mean.

## Opening the Comparison View

1. Load an event log (see [Upload Your Event Log](/how-to/upload-your-log)).
2. Click **Compare** in the top toolbar. A split panel opens with an algorithm selector on each side.
3. Choose a different algorithm for each panel. Both run against the same loaded log.
4. Hit **Run Both** or trigger each panel independently with its own **Run** button.

You can open up to four comparison panels simultaneously by clicking **Add Panel**.

## Algorithm Overview

The three primary discovery algorithms available in the playground cover different points in the fitness-precision trade-off space.

### Alpha Miner

The Alpha Miner constructs a Petri net directly from the directly-follows ordering in the log. It is fast and produces compact models, but it cannot handle loops, non-free-choice constructs, or low-frequency behaviour.

**Use Alpha when:**
- Your log has no loops and no concurrent branches that share activities.
- You want the fastest possible model for a quick sanity check.
- You are teaching process mining fundamentals and want a model that maps directly to the theory.

### Heuristic Miner

The Heuristic Miner builds a heuristics net using dependency scores between activity pairs. Rare paths can be filtered via the `dependency_threshold` parameter (0.2–0.4 recommended). It tolerates noise and loops far better than Alpha.

**Use Heuristic when:**
- Your log contains noise (incomplete cases, data-entry errors).
- You want control over the threshold between main path and noise.
- You need a model quickly but Alpha is producing spaghetti.

### Inductive Miner

The Inductive Miner recursively splits the log using process tree cuts (sequence, exclusive choice, parallel, loop). It guarantees a sound, block-structured process tree that can always be converted to a sound Petri net. This makes it the most robust algorithm in the playground.

**Use Inductive when:**
- Soundness (no deadlocks, no livelocks) is a hard requirement.
- Your log has loops and concurrency.
- You need a model suitable for conformance checking downstream.

## Quality Dimension Table

Every algorithm run emits four quality scores visible in the **Quality** panel below each result.

| Dimension | What It Measures | Alpha | Heuristic | Inductive |
|-----------|-----------------|-------|-----------|-----------|
| **Fitness** | How much of the log the model can replay (0–1) | Low–Med | Med–High | High |
| **Precision** | How much the model allows beyond the log (0–1, higher = tighter) | High | Med | Med–High |
| **Generalization** | Whether the model covers unseen-but-plausible variants | Low | Med | High |
| **Simplicity** | Inverse arc density — fewer arcs = simpler (0–1) | High | Med | Med |

A perfect model scores 1.0 on all four. In practice, fitness and precision trade against each other: a model that replays everything is often imprecise (allows too much), and a highly precise model may not replay noisy traces.

The playground renders a radar chart for each algorithm so you can see the shape of the trade-off at a glance.

## Tips for Meaningful Comparisons

- **Fix the log, vary the algorithm.** Always compare algorithms on the same unmodified log. Reloading a different preset between runs will invalidate the comparison.
- **Check the fitness threshold.** The wasm4pm kernel enforces a fitness threshold of `> 0.85` for a model to be marked valid. If an algorithm falls below this, the quality badge turns red. This is not a bug — it means the algorithm's assumptions do not match your log.
- **Export both models.** Use the **Export PNML** button on each panel to download the Petri nets for further analysis in ProM or pm4py.
- **Use the diff view.** When two panels are both showing Petri nets, the **Diff** button highlights arcs that appear in one model but not the other.

# Why WebAssembly?

## The deployment problem

Classic process mining tools (ProM, pm4py, Disco) require a local install: Java or Python, dependencies, data files. Analysts hit friction before they see a single DFG.

A web service solves the install problem but creates new ones: privacy (your event log leaves your machine), latency (every run is a round-trip), and operational cost (you must run a server).

WebAssembly eliminates both problems.

## What WASM gives you

**Portability** — The same `wasm4pm_bg.wasm` binary runs in Chrome, Firefox, Safari, Node.js, Deno, and Wasmtime. One build, every runtime.

**Performance** — WASM executes at near-native speed. The `simd_streaming_dfg` algorithm uses 128-bit SIMD instructions where available. A 100-trace log processes in milliseconds.

**Determinism** — WASM has no global mutable state outside the linear memory. Given the same input and the same memory layout, WASM produces bit-exact output. This is the foundation of the BLAKE3 receipt chain.

**Privacy** — Your event log never leaves your browser. The WASM binary is downloaded once and cached; subsequent runs are fully offline.

## The wasm-pack build

The Rust core is compiled with:
```bash
wasm-pack build --target bundler --out-dir pkg
```

The `bundler` target produces:
- `wasm4pm_bg.wasm` — the binary (~8MB, all 60 algorithms)
- `wasm4pm_bg.js` — raw WASM glue (642KB)
- `wasm4pm.js` — ES module entry (173 bytes)

The `nodejs` target is used for the CLI and server routes.

## SSR guard

Because WASM cannot run during server-side rendering (there is no `WebAssembly` global on the Nuxt server), every WASM call is guarded:

```typescript
if (import.meta.server) return
```

The composable `useWasm()` enforces this. WASM initializes once per browser session via a module-level singleton — subsequent calls return the cached module instantly.

## Product requirement

`wasm4pm` SHALL be the executable process-intelligence and process-mining engine of the Chatman Ecosystem. By v2030.1.1 it must turn admitted process/event structures into real bounded algorithm execution through Rust/WASM and generated TypeScript/CLI surfaces while preserving typed refusals, deterministic behavior where declared, provenance, and exact runtime evidence.

## Required capabilities

1. Consume structural/process type law from `wasm4pm-compat` without duplicating its canonical compatibility model.
2. Execute process-mining and object-centric process capabilities over admitted inputs, with real runtime boundaries for claimed behavior.
3. Support OCEL/object-centric process models, conformance, discovery, analytics, simulation, and cognition/process composition where admitted by the product.
4. Maintain consistent semantic operations across Rust/WASM, TypeScript, CLI, APIs, and generated cognition interfaces where those surfaces exist.
5. Preserve stable typed refusal codes across wrappers; a WASM refusal SHALL NOT become wrapper success.
6. Preserve deterministic collections, seeds, serialization, and receipt identity for deterministic paths.
7. Bind paper-grounded algorithms to provenance and executable fixtures when research claims are productized.
8. Export process execution evidence consumable by `affidavit`, `praxis`, AutoFDE, and FDEGym.

## Architecture requirements

```text
admitted process/event input
      -> compat structural boundary
      -> Rust process core
      -> WASM / native execution
      -> generated host interfaces
      -> observed result
      -> receipt / replay
```

Generated cognition/registry surfaces SHALL remain projections of their admitted ggen source and SHALL NOT be hand-edited. Wrapper tests cannot substitute for the real WASM/native boundary when the claim names that boundary.

The runtime SHALL distinguish process computation from external enterprise actuation. Computing a repair, plan, or process recommendation is CONSTRUCT; changing an external system requires the owning BRCE authority path.

## Acceptance for v2030.1.1

- representative process capabilities execute through the actual Rust/WASM boundary;
- host CLI/TS/API surfaces preserve core success/refusal semantics;
- generated surfaces reproduce from canonical source and fail drift checks;
- positive, negative, property/invariant, and integration fixtures exercise the claimed boundary;
- deterministic runs replay under fixed input/seed/toolchain identity;
- process outputs include enough provenance for independent verification;
- composed pipelines are tested as compositions rather than inferred from per-component success;
- published/packaged artifact claims bind the actual packed artifact, not merely repository source.

## Falsifiers

The architecture is falsified if a wrapper hides a core refusal; if a process capability is declared ALIVE from source presence or mocks without actual boundary execution; if generated cognition diverges from canonical ontology; or if process computation silently acquires external production authority.

## Ecosystem contract

`wasm4pm-compat` supplies structural law. `process-intelligence` supplies research/process knowledge. `wasm4pm` owns executable process behavior. Formal certification and external actuation remain independent boundaries.

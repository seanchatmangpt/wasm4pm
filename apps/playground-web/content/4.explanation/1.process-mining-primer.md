# Process Mining Primer

Process mining is the discipline of deriving process knowledge from event data — **not from interviews, not from flowcharts, but from the digital footprints left by real work**.

Every time a system records "order placed at 09:12, payment received at 09:47, shipment dispatched at 10:03", it is writing an event log. Process mining turns thousands of those traces into verifiable process models, conformance scores, and performance insights — automatically, from evidence.

## The three tasks

### Discovery

**Given an event log, produce a process model that explains it.**

Output: Petri net, DFG, POWL, or process tree.

**Concrete example:** An insurance company's claims system has logged 50,000 case traces over six months. You feed that log to the Alpha Miner or Heuristic Miner. The algorithm finds that "Assess Damage" always follows "Register Claim", but "Request Additional Documents" sometimes loops back before "Approve Payout". The discovered DFG shows this loop explicitly — something the official process diagram never mentioned.

Discovery asks: *what process does the data actually show?*

### Conformance Checking

**Given a log and a model, measure how well they agree.**

Output: fitness score, alignment costs, deviation map.

**Concrete example:** The same insurance company has a normative BPMN model that says "Fraud Check" must always run before "Approve Payout". You replay the event log against this model using token-based replay or alignment-based conformance. The result: fitness = 0.74. That means 26% of traces deviate — in this case, by skipping the fraud check. The alignment costs reveal which cases deviated and at which step.

Conformance asks: *does the real process obey the declared process?*

### Enhancement

**Given a conforming model and a log, enrich the model with performance data.**

Output: annotated model with throughput times, waiting times, resource utilization.

**Concrete example:** After conformance checking confirms the model is valid (fitness > 0.85), you replay the log again — this time recording timestamps at each transition. The enhanced model shows that "Assess Damage" takes a median of 4.2 hours but has a 95th-percentile of 3 days. The bottleneck is identifiable: certain assessors have 10× the queue depth of others. This is insight no interview could reliably surface.

Enhancement asks: *where is the process slow, expensive, or resource-constrained?*

## Why this matters

A process model drawn on a whiteboard is a hypothesis. Process mining tests that hypothesis against evidence. When the log says the model is wrong, the log wins.

> "If the code says it worked but the event log cannot prove a lawful process happened, then it did not work." — wasm4pm Chicago TDD doctrine

This principle applies beyond testing. Any claim about how a process works — in documentation, in compliance reports, in architecture diagrams — is only as good as the event log that can confirm it. Process mining is how you close that loop.

## Quality dimensions

Van der Aalst (2016) defines four quality dimensions for discovered process models:

| Dimension | Question | Trade-off |
|-----------|---------|-----------|
| **Fitness** | Does the model replay the log? | Higher = more faithful |
| **Precision** | Does the model avoid unseen behavior? | Higher = less permissive |
| **Simplicity** | Is the model easy to understand? | Higher = fewer constructs |
| **Generalization** | Does the model generalize beyond the log? | Higher = more abstract |

These four dimensions are in tension. A model that replays everything perfectly (fitness = 1.0) may allow enormous amounts of unseen behavior (low precision). A very precise model may not generalize. Good process mining practice means making the trade-off explicit rather than optimizing one dimension blindly.

## Conformance Checking

Conformance checking is the process mining task most directly tied to accountability. It answers: *did the real process match what was promised?*

Two main techniques exist:

- **Token-based replay** — Simulate the model with tokens; count missing and remaining tokens at the end of each trace. Fast, approximate.
- **Alignment-based conformance** — Find the optimal alignment between each trace and the model using cost-minimizing search. Exact, slower.

wasm4pm implements alignment-based conformance via `compute_conformance_alignments()`. Token-based replay is available via `token_based_replay()`.

::ConformanceExplainer{}

## XES vs OCEL 2.0

**XES** — One case = one trace. Events have exactly one case identifier. Suitable for linear processes (order fulfillment, loan application).

**OCEL 2.0** — One event can involve multiple objects of multiple types. A "payment" event might relate to an order object, a customer object, and an invoice object simultaneously. Required for any process with complex object interactions.

The difference matters: many real enterprise processes are inherently multi-object. A purchase-to-pay process involves purchase orders, goods receipts, invoices, and payments — all interacting. Flattening this to XES loses the cross-object causality that makes conformance checking meaningful.

wasm4pm supports both. Pass XES to `load_eventlog_from_xes()`; pass OCEL JSON to `load_ocel()`.

## Where wasm4pm fits

wasm4pm is a **browser-native process mining runtime**. The 60 algorithms run in WebAssembly — the same binary in a Node.js CLI and in your browser tab. No server round-trip for computation.

The architecture:
1. **Rust/WASM core** (`wasm4pm/`) — 60 algorithms, deterministic, bit-exact
2. **TypeScript monorepo** — CLI, kernel, planner, observability, cognition
3. **Browser playground** (you are here) — MDC docs + live WASM demos

Every computation emits a BLAKE3 receipt. If the receipt doesn't exist, the computation didn't happen.

# Parity Surface Reconciliation

## 1. Clean Stack Statement
This document reconciles the ingestion and validation surfaces for the `wasm4pm` ecosystem. It establishes the distinct roles of `wasm4pm`, `wasm4pm-compat`, and `pm4py-lsp` in ensuring parity between the empirical Python reference implementation (PM4Py) and the Rust/WASM execution engine.

There are two distinct and lawful input streams that `wasm4pm` must support:
1. **Raw Process Evidence:** Data entering via `wasm4pm-compat` for typed admission and subsequent execution.
2. **Empirical Parity Fixtures:** PM4Py behavior snapshots generated by `pm4py-lsp` acting as the ground-truth reference for parity validation.

## 2. Boundary Invariants
- **tower-lsp-max:** Pure LSP protocol substrate. Does not know about PM4Py or process mining.
- **pm4py-lsp:** The empirical witness generator. It observes PM4Py behavior, generates deterministic snapshots, and produces parity fixtures.
- **wasm4pm-compat:** The court of admissibility. It defines the typed structures, loss policies, and receipt envelopes for process evidence. It is strictly structural.
- **wasm4pm:** The sovereign execution authority. It consumes admitted evidence or graduation candidates from `wasm4pm-compat` and parity fixtures from `pm4py-lsp`. It executes discovery/conformance/replay and produces verifiable results.

## 3. Fixture Contract Summary
`pm4py-lsp` produces parity fixtures in the following schema:
- **Location:** `fixtures/pm4py-parity/<snapshot_hash>.json`
- **Schema:**
  - `schema_version`: String
  - `snapshot_id`: String (Hash)
  - `source_uri`: String
  - `source_hash`: String
  - `csv_path` / `log_path`: String
  - `pandas_alias`: String
  - `pm4py_alias`: String
  - `discovery_calls`: Array of operational parameters
  - `mapping_parameters`: Object defining the configuration
  - `expected_artifact_class`: String (e.g., `ProcessTree`, `PetriNet`)
  - `unknowns`: Metadata for unsupported or unmapped PM4Py arguments
  - `expected_outcome` / `result`: The actual serialized artifact or behavioral metric produced by PM4Py.

## 4. wasm4pm Consumption Plan
To maintain the boundary law, `wasm4pm` will consume fixtures through a dedicated test harness (`ParityReplayHarness`):
1. **Load:** The harness reads the fixture from disk.
2. **Setup:** It loads the referenced `csv_path` or `log_path` through `wasm4pm-compat`'s admission pipeline to create `AdmittedEvidence`.
3. **Execution:** It maps the `discovery_calls` and `mapping_parameters` to the corresponding `wasm4pm` algorithm execution surface.
4. **Comparison:** It compares the `wasm4pm` execution result against the `expected_outcome` defined in the fixture.
5. **Verdict:** It generates a `ParityVerdict` receipt (Pass/Fail/Shift).

## 5. Anti-Overclaim Gate
- **Do not claim parity is complete.** The bridge is only complete when `wasm4pm` consumes a fixture, executes the corresponding algorithm, and demonstrably passes the comparison.
- **Do not treat benchmark absence as PASS.**
- **Do not treat stress skipped as PASS.**
- **Unknown != Admitted.** Unmapped parameters from PM4Py must be explicitly documented and rejected if they alter expected behavior.
- **Unsupported != Refused.** If PM4Py supports an operation that `wasm4pm` does not, it is a coverage gap, not a structural refusal.
